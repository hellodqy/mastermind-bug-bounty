# Vulnerability Report Writing Guide

> Integrated from the standalone `vuln-report-writing` Skill. Load only when producing a vulnerability report.

依据目标 SRC 报告写作风格与平台五段式模板提炼。目标：审核人员**仅凭报告即可独立复现**，证据链完整、可直接放行/定级。

---

## 一、何时使用本技能

- 已确认一个漏洞、拿到完整利用链 + 关键证据（数据包/响应/轨迹）后，要把发现写成可提交的报告；
- 或已有一堆零散数据包/截图，需要组织成规范报告；
- 产出物 = 一份结构化 Markdown/Word 报告正文（含图位占位），可直接粘贴或转 docx 提交。

## 二、需要的输入（写之前先齐这些）

写报告前先核对，缺的从任务轨迹/发现里补：
1. 受影响资产：具体可访问 URL/域名/**接口路径**（不是泛泛的系统名）；
2. 完整 raw 请求（方法/路径/Host/关键头/body 全量）+ 关键响应回显；
3. 完整攻击链的每一步动作与结果（尤其是"从哪一步发现什么"）；
4. 需要放截图的关键帧说明（登录页/JS常量/拦截报错/绕过后成功/批量数据/危害落地）；
5. 危害影响面 + 修复方向。
6. 若输入只有发现描述（summary/evidence），按本文档骨架补全叙述与图位。
7、poc不要用curl，尽量用完整burp数据包（只需要请求的数据包，不需要响应的数据包），而且详情要写明从资产来源开始的漏洞发现过程，比如接口来源（访问xxx页面，加载了xxx.js，获取到xx接口）

---

## 三、报告结构（五段式，主模板）

```
【标题】[系统/平台名]存在[漏洞类]，[最大危害一句话]

一、漏洞摘要【必填】
二、受影响资产【必填】
三、复现手册【必填】（报告主体，占 ~80%）
四、附件POC（可选：数据包/脚本/录屏打包 zip + README.txt 说明对应步骤）
五、风险影响评估【必填】
六、修复建议【选填】
```

> 若目标平台自带官方模板（如 OPPO 五段式里要求复现手册含：测试环境/操作步骤/预期结果&实际结果、附件POC），**优先沿用平台章节名**，本技能的结构与之兼容。

### 标题规范
- 句式：`[资产/系统] + 存在 + [漏洞类] + , + [攻击者能做什么/最大后果]`
- 例：`OPPO电子签章系统存在未授权访问，可完整接管电子签服务`
- 直接上最高危影响，不绕弯；属于某联合/专项可加前缀如【八周年联合】。

### 一、漏洞摘要（1~2 句讲完五要素）
**哪个系统 + 哪个端点 + 什么漏洞 + 能拿到什么/能做什么 + 影响规模**。
- 句式偏好："XX平台存在XX漏洞，可XXX（未授权读取/接管/批量枚举），导致XXX泄露/业务XX。"
- 用"仅凭 xxx 即可…"突出易利用性；有多个同源端点合并表述。

### 二、受影响资产
- 直接列**具体端点**（域/完整 URL/接口路径），一个一行；不写无关内容。
- 例：`gbaas-file-mwps-stable.wanyol.com/file/mobile/file/*`

---

## 四、复现手册【黄金攻击链】（核心）

每篇报告按同一条叙事链写，保证可复现 + 可信：

```
① 信息收集起点   → 怎么找到这个资产/接口（来源站、根域侦察、子域枚举）
② 定位服务/JS    → 从 JS/配置文件扒出：真实后端网关、路由前缀、AppId、签名算法、接口契约
③ 找到漏洞点     → 未授权接口/绕过点；先证明"默认有限制"再给绕过方式
④ 构造请求       → 完整 raw 数据包（可直接重放）
⑤ 验证成功       → 响应里的关键敏感字段/成功标志（配图位）
⑥ 危害放大       → 遍历 userId/工号/orgId、批量枚举、全量列表、写操作证明
⑦ 收尾合规       → "合规测试仅做可读证明/未实际测试/已还原"
```

**每步的写法 = "动作 → 结果 → 证据(URL / raw包 / 〔图〕)"**，不要写空话。

### 各步要点与必备图位

**① 信息收集**：写出资产从哪来（如"对 oppo 资产信息收集发现 xx 域名"、"wanyol.com 根域子域枚举+JS 分析定位"）。放图：目标站点首页/登录页（证明系统真实在跑）。

**② JS / 配置分析**：这是样本里出现率最高的手法——写清**从哪个 JS 文件**（带完整 URL）扒到了什么：
- 网关前缀 / 真实后端地址（常与线上同 IP、dev 直接挂生产网关后）；
- 微服务目录（一次性泄露几十个模块）；
- AppId / 请求头约定（如 `headers.AppId="oppo-it-mo"`）；
- 接口契约（路由 + 参数 + 查询类型）；
- 签名算法/密钥材料（硬编码常量、rsa 公钥、时间戳+hmac）。
放图：JS/配置里关键常量那一段（高亮 appid/网关/签名）。

**③ 找到漏洞点（含"防御存在"的证据，最能加分）**：
- 直接调接口 → 401/403/“权限认证失败” → 说明**本来有校验**（证明不是目标没做任何防护，而是可被绕/漏配）；
- 分析绕过根因并一句话讲清，例如：
  - "权限校验仅判断 Authorization 是否为空 → 带上任意非空值即过"；
  - "`@Inner` 内部调用约定 from:Y → 加头直达业务层"；
  - "白名单只判断了是否包含 → `#`/`@` 绕过";
  - "公钥加密当认证、公钥随客户端下发 → 人人可离线伪造"。
  放图：第一次被拦截的报错/401/403 截图。

**④ 构造请求**：见下方【数据包规范】。

**⑤ 验证成功**：放响应截图，图中要能看到关键敏感字段/成功回显（列表、手机号、合同、token 等）。

**⑥ 危害放大（决定定级的关键）**：一定要论证"不是偶发一条，而是全量/可遍历/实时"：
- userId/工号/供应商代码/orgId 递增可遍历 → 附批量请求包；
- 读全量清单（`getPreviewFileList`、`sign-flow-list`）→ 证明可完整接管；
- 存在写接口 → 补一句可写/可伪造（配合三性评估）。
放图：批量/遍历/全量数据的列表截图。

**⑦ 收尾合规（责任边界，必写）**：模板句见下方。

### 复杂漏洞加两节
业务链路长、牵扯多套系统或需逆向客户端（打印客户端/Electron/小程序）时，在复现手册开头补：
- **业务背景**：系统是干嘛的、数据怎么流转（如"收银系统经 STOMP/WebSocket 推打印任务到门店客户端"）；
- **漏洞成因（设计缺陷叠加）**：用 1. 2. 3. 分条列 root cause 和判断依据（如"把加密当认证""无按门店订阅鉴权""写接口 noLogin"），每条给证据来源（exe 内 asar、js 文件）。
- 结尾可给"影响面扩散"：同源同缺陷多套环境（prod/pre/区域站）。

## 五、数据包 / 脚本规范（报告中最高优先级的内容）

1. **raw 包全量贴出**，保持原始格式，可删 Cookie 但**关键头一个不省**（如 `Authorization`、`from: Y`、`Tenant-Id`、`X-Tsign-Open-App-Id`、`Content-MD5` 等签名/绕过用头）；
2. 方法/路径/Host/headers/空行/body 排版对齐 HTTP 原样；
3. 有**签名/加密/时间戳**计算的（hmac/sha256/md5/RSA/OSS policy），附一行可直接复跑的：
   ```
   python -X utf8 -c "import hmac,hashlib,base64,time,json;..."
   ```
   并注明"输出第一行=requestTimeStamp、第二行=token"之类的字段对应关系，再给带入后的完整包；
4. 复杂利用给脚本文件（如 `drp_stomp_exploit.py`），在报告里说明运行方式、改哪两行可切换环境、预期输出；
5. 需要 base64 解码展示的（policy/callback）可贴原文+解码结果。

## 六、图位占位规约（重要）

**不需要真的插入截图**：凡报告中需要图的地方，插入统一格式的占位符，说明该位置该截什么图，交由提交者补图。

推荐两种占位格式（二选一，全篇统一）：
```
〔图1〕此处放图：xxx 首页/登录页截图
〔图2〕此处放图：Burp 中该请求的响应，需能看到 xxx 字段
```
或行内写法：
```
【📷 截图：从 newApprovalData.js 中定位到网关前缀与 AppId 的代码段】
```
- 每个图位**必须写清期望截图内容**（谁、什么界面/包、能看到什么字段），不能只写"截图"；
- 报告开头注明："文中〔图n〕为占位标记，请按说明截图后替换。"
- 占位符锚定在证据对应的叙述行之后，保证"话在哪、图在哪"。

### 默认图位清单（按攻击链排序）
1. 目标站点首页/登录页（证明系统真实）；
2. JS/配置文件中定位到关键常量/网关/AppId/签名的片段；
3. 默认访问被拒（401/403/报错）→ 证明防御存在；
4. 绕过/未授权后请求成功，响应含敏感字段；
5. 遍历/批量/全量枚举拿到的数据列表（放大影响）；
6. 危害落地物（下载到的合同/文档/打印订单/档案详情）；
7. （如有）利用脚本的运行输出。

## 七、各漏洞类型的复现骨架（速查）

| 漏洞类型                | 复现链要点                                                   |
| ----------------------- | ------------------------------------------------------------ |
| 未授权访问/敏感信息泄露 | 资产→JS/接口契约→**不带凭证直接调**→响应含数据→批量证明（遍历 id/工号/keyword 全量） |
| 认证/权限绕过           | 先演示"正常被拒"→讲绕过原理（仅判空/固定头 `from:Y`/畸形请求触发堆栈泄框架）→给绕过后的包 |
| IDOR/越权               | 正常调用（低权/本人）→ 换 id/工号读他人数据 → 说明可遍历     |
| URL 跳转                | 正常跳转 → 指出白名单校验缺陷（包含判断/`#`/`@`/双写）→ 构造 payload 成功跳 evil |
| 任意文件上传            | 正常上传拿到 OSS policy/signature → **替换 policy/signature/callback/key** → 上传 → 访问落地 URL（注意是否映射到主域/同源）→ 论证可钓鱼/存储 XSS |
| Swagger/API 泄露        | 发现单点→枚举全部模块（`swagger-resources`→`v2/api-docs`）→ 列出未鉴权可打接口 |
| 高权限接管/复杂链路     | 五段式 + 业务背景 + 漏洞成因分条 + 影响面（多环境/多区域同源） |

### 风险影响评估（五）写法
从三性分角度列点（1. 2. 3.），句式 = "攻击者可…→ 真实业务后果 → 规模"：
- **机密性**：泄露哪些敏感数据、是否全量、是否可遍历/实时流；
- **完整性**：能否写/改/伪造（伪造盖章合同、投毒文档、篡改机构配置、劫持打印任务）；
- **可用性**：业务中断、恶意跳转钓鱼、打印链路 DoS、账号接管。
善用**有依据的量化词**："所有/全量/实时/全国门店/无需凭证"。宁可少说不要虚报。

### 修复建议（六）写法
- **原理性修复**，非"加个 WAF 规则/封这个 IP"这种临时规避；
- 简单漏洞一句：如"完善 XX 接口的权限校验措施"；
- 复杂漏洞分条：认证改造（私钥签名/服务端验签+mTLS）→ 授权拦截（按身份校验订阅/归属）→ 最小权限（拆分 token）→ 审计告警。

## 八、合规与责任边界（固定措辞，视情况选）

- "因为合规测试，此处只进行了可读证明，实则 projectId/secret 还可用于多个写操作（未实际调用）。"
- "该写操作未实际测试，辛苦审核大大进行验证。"
- "只修改了 xx 字段（如语言开关），且已还原。"
- "相关数据已做脱敏/掩码处理（手机号/关键字段）。"

---

## 九、文风自检（对照历史高评级报告）

- 精简技术流：URL/数据包/代码/截图说话，动作→结果→证据；
- 保留"排查过程"：失败的尝试/被拦的包值得写一两句，证明限制真实存在、绕过点可靠；
- 关键判定给依据："公钥随公开 exe 下发 → 人人可离线伪造"；"dev 与生产同 IP → 是活后端"；
- 审核员友好：编号步骤、小标题、一步一图位、可复现；
- 不写空泛形容词与无来源的夸大影响。

## 十、提交前 Checklist

- [ ] 标题/文件名：系统 + 漏洞类 + 最大危害一句话
- [ ] 摘要含五要素（系统/端点/漏洞/可做什么/规模）
- [ ] 受影响资产是**具体可访问 URL/接口**
- [ ] 复现手册从信息收集到结果，每步有证据（URL 或 raw 包或〔图〕占位）
- [ ] 关键 raw 数据包完整、关键头齐全、可重放；签名类附可复跑命令
- [ ] 图位占位符已写清"该位置截什么图"
- [ ] 有合规边界/已还原说明
- [ ] 风险从机密/完整/可用三性写、有量化词
- [ ] 修复建议为原理性
