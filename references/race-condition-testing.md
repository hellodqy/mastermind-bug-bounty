# Race Condition Testing

用于一次性动作、余额/库存、验证码、审批和状态转换。重点是可靠同步与可量化的服务端不变量破坏。

## 1. 前置条件

先证明单次正常行为，记录请求、幂等键、响应、服务端最终状态和恢复方式。选择测试账号、自建对象或沙箱权益。

## 2. 同步方法

- 多连接 gate：先建立请求，在尽可能接近提交点时同时释放；
- last-byte synchronization：各请求保留最后少量数据，再同时发送；
- HTTP/2 single-packet：同一连接多 stream 协调完成，但仅在客户端和服务端确实支持时使用；
- 顺序对照：相同数量的串行请求用于排除正常重试与最终一致性。

工具显示“并发发送”不等于请求到达临界区；证据必须来自服务端最终状态。

## 3. 高价值不变量

一次性 token 只能消费一次、余额不能双花、库存/配额不能超限、验证码/邀请不能重复兑现、审批和状态迁移必须原子化、幂等键必须绑定主体和动作。

## 4. 安全边界

从两个请求开始，只增加到证明所需的最小并发。不得影响真实资金、库存、他人权益或服务可用性。异常权益不提现、不转移，并在可行时回滚。

## 5. 报告

量化正常值、并发数、成功数和最终异常状态；排除客户端重复显示、异步延迟和正常幂等重试。说明被破坏的业务不变量，而不是只写“存在竞态”。
